You don’t need long context
Peter Belcak, Saurav Muralidharan, Jindong Jiang, Y onggan F u, W onmin Byeon, Hanrong Y e,
Ryan Angilly , Ali T aghibakhshi, Shih-Y ang Liu, Siru Ouyang, Greg Heinrich, Pavlo Molchanov
Abstract.Later tokens are costlier to generate than earlier tokens. On frontier open weight models, the
disparity in cost may rise to as much as 7x. Through frequent compaction, we show across a broad range
of long-horizon and long-input tasks that frontier language models sacrifice little to no task accuracy when
maintaining short contexts. We further demonstrate that LLM performance does not collapse on long-horizon
software engineering tasks even when taking at most one action per context, and based on that we outline the
concept of semantic state space models (SSSMs). Our findings question the need for long-context language
models.

1. Introduction
Not all tokens are generated equal. Token generation latency and memory footprint both grow with the
number of tokens in a language model’s context. This is due to the inherent linear1 relationship between the
computational cost of generating a token and its depth within a context [25]. Figure 1 shows the cloud token
generation cost as a function of context window size for a selection of popular open-weight models. Observe
that there is a considerable monetary benefit to serving models on cloud GPUs with consistently shorter
contexts. This fact is often hidden from the end user since retail token prices are quoted at a fixed price per
1M tokens regardless of the input context length. Note that the extent of cost reductions (3.6× to7 ×) rivals
or exceeds that of many other orthogonal optimization methods such as aggressive quantization or structured
sparsification [5, 14, 8].

Put simply, the longer the input context provided to the language model (LM), the slower, more memory
hungry, and more expensive its output token generation.
Given the considerable benefits of keeping input context short in both cloud and edge LM use, one would
assume that popular LMs would have naturally evolved to operate on contexts only as short as necessary to
complete their tasks. This could not be farther from the truth. As seen in Table 1, which compares the lengths
of well-known works of writing with the context window sizes of representative proprietary and open-weight
models, context window sizes have vastly outgrown many influential writings. It would seem that models have
been evolving to accommodate the ever larger possible inputs rather than to maximize efficiency.
The enormous context window sizes of contemporary LMs and the tangible cost advantages of keeping their
contexts short thus appear to be at odds with each other. While operating with longer contexts might in
some cases be thoughtbeneficialto model task accuracy, we must ask:
RQ0Are long contextsnecessary?
If not, let’s do away with long contexts and long-context models. And, if there are currently any objective
benefits of keeping long context models, we can likely preserve them by making the appropriate post-training
adjustments to future models.

To answer RQ0, look at where the so-called long contexts (and, correspondingly, large context windows) in
language modeling come from. Broadly, there are two types of workloads that often result in long input
contexts being passed to LMs:
LCW1 Workloads of long-horizon tasks – tasks that may require many actions in order to be completed
and where the context builds up as the model makes its way towards the completion of the
task [11, 47, 52].
LCW2 Workloads of long-input tasks – tasks that require operating across a large amount of input
information [6, 45, 29].
Examining these two types of workloads more closely, it is not immediately clear whether operating on long
contexts is necessary in order to complete them. In particular, the entire conversational history of LCW1
does not necessarily need to be considered at every step of a long-horizon operation in order to successfully
complete the task. Likewise, the long inputs of LCW2 do not necessarily need to be ingested in their entirety
at all times in order for the workload to conclude successfully. Moreover, observe that the tasks in LCW2 can
always be reduced to LCW1 by storing the long input as a resource and equipping the LM with a tool for
selective input reading.
Motivated by the advantages of keeping LM generation contexts short and the apparent lack of clear justification
for the popular practice for ingesting long inputs all at once and maintaining long conversational histories as
discussed above, we decompose RQ0 to pose the following research questions:
RQ1Can long-horizon tasks be completed without long contexts?
RQ2Can long-input tasks be completed without long contexts?
RQ3Can long-horizon tasks be completed taking no more than a single action per context?
The rest of this paper is aimed at curtly answering these questions.
2. Methodology
We use one methodology to answer all research questions posed in Section 1.
2.1. Definitions
The base term “context” is, unfortunately, considerably overloaded in language modelling. Below we outline
our working definitions intended to fix the meaning of otherwise vaguely interpreted terms commonly used in
the community and relied on throughout this paper. Their numerical boundaries are rough rules of thumb.
Inference step.Aninference stepis one invocation of an LM to produce output. In agentic workflows, it
typically coincides with one agent turn of a conversation.
Input context.At a given inference step, theinput contextis the complete sequence of tokens made available
to the LM to produce output. It may include system instructions, the task input, prior model outputs, tool
results, and any other conversational history.
Output context.At a given inference step, theoutput contextis the complete sequence of tokens generated
by the LM in the inference step. It may include a thinking trace, tool calls, user-oriented outputs, or other
model output artifacts.
Context.At a given inference step, thecontextis the input context, the input context and an associated
output context, or the input context and any token space reserved for a possible output context.
Context window and context window size.Thecontext windowis the space of tokens an LM can
comprehend at any given point, usually imposed by the model’s architecture or indirectly by its post-training
data bias. Contexts exceeding context windows may cause system errors or unexpected behavior. Thecontext
window sizeis the maximum number of tokens that an LM endpoint can process in one invocation, whether
imposed by the model’s context window or narrowed by its serving configuration.

Long context.We call a contextlongwhen its length approaches constituting a significant fraction of
context window size of many contemporary frontier models, which tends to rest at approximately256K tokens
or more at the time of this study. We further call an execution regime or context-management strategy
long-contextif it permits the context to grow toward that scale, even when an individual run terminates
before reaching the context window size.
Short context.We call a contextshortwhen its length is much closer to zero than to the context window
size common to many contemporary frontier models. In the operating regimes emphasized in this work, short
contexts are commonly limited to roughly16K–50K tokens. Note that we take “short” to mean short relative
to common context window sizes; it does not mean that the context is small in an absolute linguistic sense.
Even context window sizes of16K–50K tokens suffice to contain elaborate literary works (cf. Table 1).
Long-input task.Along input taskis a task which is accompanied by along input– i.e., input information
that would constitute a long context if ingested directly. The termlong inputrefers to the size of the available
task input, irrespective of whether a harness places all of it in the model context at once or exposes it through
selective input reading.
Long-horizon task.Along-horizon taskis a task whose completion requires many sequential model actions,
with later actions depending on the observations, artifacts, or decisions produced by earlier ones. Absent
context management, the resulting interaction history accumulates across the task and may grow toward a
model’s context window size and form a long context.
2.2. Benchmarks
We assess the merits of RQ1–RQ3 by considering two groups of benchmarks corresponding to the sources of
long context identified in Section 1: long-horizon tasks (LCW1), whose interaction histories grow as an agent
acts, and long-input tasks (LCW2), whose source material can itself fill or exceed a model’s context window
size. Our ensemble of benchmarks covers realistic software-engineering, information-seeking, and tool-use
workloads with controlled long-input diagnostics.
Long-horizon task benchmarks.The long-horizon task benchmark group aims to represent real sequential
workflows in which the model must repeatedly inspect an environment, select an action, observe its result,
and use that result to decide what to do next. Without context management, every command, tool response,
retrieved document, and intermediate decision is appended to an ever-growing history. The software-engineering
benchmarks are particularly representative examples because repository exploration, implementation, and
validation naturally form long sequences of interdependent actions. The remaining benchmarks broaden this
group to information retrieval, user interaction, and cross-tool orchestration.
• SWE-bench Verified[23] is a human-validated set of 500 real GitHub issue-resolution tasks from
popular repositories, where the agent must produce a patch that passes the repository’s held-out test
suite.
• SWE-bench Multilingual[48] comprises 300 manually curated issue-resolution tasks from repositories
across nine programming languages. It tests repository exploration, implementation, and validation
across different language ecosystems.
• Terminal-Bench 2.1[30] is an agentic benchmark of 89 real command-line tasks executed in sandboxed
containers and scored by per-task verifiers, measuring end-to-end terminal problem-solving beyond
single-repository patching.
• FRAMES[ 27] contains 824 challenging multi-hop questions whose answers require combining infor-
mation from two to fifteen Wikipedia articles. In our agentic formulation, the model searches a fixed
Wikipedia corpus, opens relevant articles incrementally, and submits a free-form answer evaluated
against the reference answer by an LM judge. The benchmark consequently tests iterative retrieval and
evidence integration while allowing the retrieved evidence to accumulate in the interaction history.
•𝜏 2-bench[ 7] evaluates agents that converse with a simulated user while operating domain-specific
tools under explicit policy constraints. We use the 184-task golden set spanning retail, airline, and
telecommunications; success requires both satisfying the user’s request and bringing the environment to
the correct final state. Its mixture of dialogue, reasoning, and state-changing tool calls tests whether
information established early in an interaction remains usable by later actions.
• BFCLv3[ 36] evaluates multi-turn tool use in simulated environments. We use its 200 long-context
episodes, which require agents to retain information across user turns and schedule state-changing tool

Long-input task benchmarks.The long-input task benchmark group holds the task question comparatively
short while making the information needed to answer it large, at least in principle. It includes three broad,

• LongBench v2[6] comprises 503 challenging multiple-choice questions with heterogeneous, predomi-
nantly natural inputs ranging from8K to approximately2M words. Its six task families cover single-
and multi-document question answering, long in-context learning, long dialogue, code-repository under-
standing, and structured-data understanding.
• LOONG[ 45] is a 1,600-question multi-document benchmark in which a question typically depends on
multiple complete financial reports, legal cases, or academic papers in either English or Chinese. Its
locating, comparison, clustering, and chain-of-reasoning tasks are designed so that evidence is distributed
across multiple load-bearing documents.
• Artificial Analysis Long Context Reasoning (AA-LCR)[4] comprises 100 human-crafted questions
requiring reasoning across sets of real-world documents averaging approximately100K input tokens. Its
seven document categories include company and industry reports, government consultations, academic
and legal documents, marketing materials, and survey reports. Answers require integrating evidence
and performing multi-step reasoning across documents, rather than retrieving a directly stated fact.
• Needle in a Haystack (NIAH)[24] consists of target sentences inserted at controlled depths in long
bodies of unrelated essay text and of asking for the fact expressed by that sentence. Our 125-instance
grid varies both insertion depth and document length, with contexts extending from16K to roughly
500K tokens.
• RULER[ 22] is a synthetic long-context suite containing thirteen tasks: eight needle-retrieval variants,
variable tracking, common- and frequent-word extraction, and two multi-hop question-answering tasks.
We evaluate all thirteen at256K and500K tokens and score the recall of the required answer set.
• Counting-Stars[ 39] scatters 32 marked numbers throughout a long text and asks the model to recover
them all. We use the complete 192-question public set, spanning English and Chinese, acquisition and
reasoning variants, and documents from4K to128K tokens. The reasoning variant includes initially
incorrect counts that are subsequently corrected, requiring the model to distinguish the final value from
a nearby distractor rather than merely copy every marked number.
• BABILong[ 28] consists of short facts from the bAbI [46] reasoning tasks embedded into book text.
Answering requires locating the relevant statements and then performing operations such as fact chaining,
counting, negation, or set tracking. We evaluate 550 questions across all ten task types and five input
lengths from64K to1M tokens.
Note that even the needle-style benchmarks considered often do not feature a clear lexical overlap aiding easy
retrieval. They do, however, require aggregation, variable tracking, or reasoning over multiple retrieved facts
for the correct answer to be produced.
2.3. Models
We perform our study on two groups of models. Large closed-weight models are used as the workers in our
principal task-accuracy experiments, while large open-weight models support the cloud system throughput

2.4. Harnesses
We use two closely related base harnesses. Both implement a minimal ReAct loop: the task is supplied in an
initial user message, the model issues one Bash action at a time, and each action and its result are appended to
the conversation [49]. When used, the Bash environment exposes the files, programs, and benchmark-specific
utilities available to the agent. Each Bash invocation treats the related standard output, return code, and any
execution error as action results.
mini-swe-agent.For software-engineering and terminal tasks, we use the releasedmini-swe-agent harness
[41], with only the environment integration required by each benchmark. Its system prompt describes the
software-engineering workflow, and its Bash environment provides the task repository or container. When
done, the agent submits its proposed pull request as a patch for evaluation.
mini-agent.For the remaining benchmarks, we use our mini-agent harness, which is a straightforward
generalization of mini-swe-agent away from software engineering. It retains the same agent loop, model
interface, and Bash interface, but uses benchmark-specific instructions, environments, and submission rules.
The instructions specify the available commands, task procedure, and required answer format. Only the
system instruction and task description are provided in the initial user message. Supporting inputs and tools
are made available through the environment. When done, an evaluation benchmark adapter recognizes the
designated submission command, extracts its payload, terminates the episode, and records the prediction in
the benchmark evaluator’s required format.

Figure 3⋃︀ Context-management regimes.The three context-management regimes considered in this work:
Full-History Accumulation (FHA), End-of-Conversation Compaction (EoCC), and Single-Action Compaction
(SAC).
Full-History Accumulation (FHA).The baseline full-history accumulation regime appends every model
action and environment observation to a single conversation for the duration of the task. No history is removed
or replaced during a run. This is the default mode of operation formini-swe-agentandmini-agent.
End-of-Conversation Compaction (EoCC).This regime follows the full-history ReAct loop until the
length of the conversational context crosses a pre-specified compaction threshold. The model is then instructed
within the active conversation to produce a bounded, task-relevant compaction of its state (see Appendix A).
A higher total context limit reserves space for this compaction turn and terminates the conversation if
compaction does not complete in time. The harness starts a fresh conversation containing the original task
and the compacted state, and execution resumes under the same system prompt. This cycle repeats whenever
the compaction threshold is crossed. We write these two values as “total context limit / compaction threshold”
in tokens.
Single-Action Compaction (SAC).This regime maintains a compact semantic state and essentially no
conversational history. Each conversation receives the task and current semantic state, performs exactly one
environment action, observes its result, and updates the semantic state. The harness then discards that
conversation and starts a fresh one for the next action. For the experiments in Section 5, we apply SAC as a
context-management regime tomini-swe-agent; the underlying agent harness, model, and task environment
otherwise remain unchanged. SAC therefore keeps the active conversational context shortest of the three
regimes and operationalizes the single-action setting of RQ3.
Context length measures.We distinguishtotal lengthfrompeak length. For a full-history baseline, total
length is the length of its execution’s conversation. For EoCC and SAC, total length is the sum of the final
lengths of all conversations created during the execution. Peak length is the length of the largest conversation
produced during the task. Both measures are expressed in thousands of tokens (K) and summarized across
tasks as mean/median/maximum or median/maximum, as indicated in each table.
2.4.2. Accommodations for long inputs
We enable selective input reading by storing each long input as one or more documents (e.g.,input01.txt,
input02.txt) in the agent’s filesystem environment rather than placing their full contents in the initial
conversation. The task message identifies the available documents, and the agent performs selective input
reading using standard Bash tools (e.g.,sed, awk, head). This method of input presentation makes selective
input reading an explicit environment action and thereby reduces a long-input workload to a long-horizon
workload. We provide the agent instructions and examples of selective reading in Appendix E.

2.5. Latency and throughput measurement
Cloud serving.For each model, we use the smallest H100 node-deployment that can hold the served
checkpoint and a KV cache at the maximum evaluated context window size: eight H100 GPUs for Qwen 3
Coder Next and sixteen for GLM 5.2 and Kimi K2.6. For each context window size, we draw request lengths
uniformly from nested prefixes of a shared token sequence, with sufficient space reserved for generation. We
prefill the longest prefix once, enable prefix caching, and require every subsequent prefix request to generate
exactly1 , 024tokens. After warm-up, we sweep request concurrency and measure sustained aggregate decode
throughput as completed output tokens divided by elapsed time. We report the highest-throughput setting
with no KV-cache preemption; repeated measurements varied by at most 2%. The results are in Figure 4.
The cost values in Figure 1 convert these throughput measurements to the cost of1M output tokens using the
stated hourly GPU price.
Local serving.On the DGX Spark, we evaluate one model instance and one request at a time. For each
model, we construct a sequence at its maximum supported length and measure generation after prefixes of
increasing length drawn from that sequence. At each length, we record the mean inter-token latency over the
next1 , 024generated tokens and the total device-memory consumption. The batch-one decode throughput in
Figure 2 is the reciprocal of the mean inter-token latency.

3. Long-horizon tasks don’t need long contexts
RQ1.Can long-horizon tasks be completed without long contexts?
Answer:Yes. Frequent compaction keeps the context short while broadly maintaining task accuracy.
Following the outline of Section 2, we evaluate EoCC on 6 benchmarks representing long-horizon workloads
and measure the performance of EoCC-modified harnesses against their baseline FHA counterparts. For each
benchmark and model, we sequentially decrease the total context token limit and the corresponding compaction
threshold to fit the total context limit. This has the effect of lowering the maximum context window needed
by the model and of triggering increasingly more frequent compactions while executing long-horizon tasks.
We describe what these compactions are designed to preserve in Appendix A. For SWE-bench Verified,
TerminalBench 2.1, SWE-bench Multilingual, and FRAMES, we evaluate the models at total context limits /
compaction thresholds (cf. Section 2.4.1) of48K/36K,32K/24K,24K/18K, and16K/12K. For BFCLv3, we
consider24K/18K,16K/12K, and12K/8K, while for Tau2Bench, we consider16K/12K,12K/8K, and8K/6K.

One pathology that could occur due to frequent compaction is that while it may successfully enforce smaller
context window size, the full workflow history might be becoming longer as a consequence of the model having
to re-do previously done tasks or to revisit previously seen information. Such behavior could result in an
increased total token spend per task, ultimately erasing some of the cost savings due to smaller context
windows. In our experimentation, this was generally not the case. Detailed per-benchmark accuracy, token

once its conversation reaches a certain restrictive threshold leads to, broadly-speaking, on-par performance in
model performance on long-horizon tasks when using frontier closed-weight models. Complementary results
for open-weight models are provided in Appendix D. It would seem that the benefits of maintaining long
contexts manifest themselves inconsistently and are not drastic so as to discourage efforts to keep the working
context short in autonomous agentic workloads. Hence our answer to RQ1: yes.
3.1. Long-horizon tasks may sometimes need the history
Long-horizon tasks may sometimes need the history, but that does not mean that they require long contexts.
Compaction is a lossy context compression method. Information will be lost as a consequence of compacting
a conversational history. Even more information will be lost if the conversational history being compacted
already contains a result of an earlier compaction.
It is not too difficult to construct a task whose accuracy is guaranteed to suffer when a compaction is performed.
Consider, for example, an agent that has access to a tool that generates coin tosses and reports the outcome
of each coin toss in its tool result. With a compaction budget fixed, the agent is guaranteed to eventually
start losing information about the outcomes of some of the coin tosses. If, at some point, the agent needs
to inspect the sequence of coin toss outcomes (e.g., access the𝑖th outcome), it is guaranteed to eventually
fail as a consequence of some compaction necessarily eliminating some of its toss outcome records, with the
compaction being the cause.
Observe, however, that any such example can be eliminated by creating a harness that keeps a record of every
message of any agentic conversation, and makes it readily accessible to the agent by the means of a selective
reading tool. The querying of the agent’s conversational history then becomes a long-input task, which we
tackle in RQ2.
In other words, there is a difference between information that needs to be a part of model context and
information that could, in principle, be retrieved selectively on a “need-to-know basis”.
Note that the findings of our experimentation above are not that “you don’t ever need to access conversational
history”, but roughly that “you don’t need to keep the entire conversational history in the context in order to
complete long-horizon tasks”.

5.1. Semantic State Space Models (SSSMs).
The above observations of Section 5 and earlier observations of Sections 3 and 4 force a reflection: If powerful
models can broadly maintain performance by compacting often or even compacting after taking a single action,
cannot all long-context workflows be coerced into becoming single-action workflows through compaction? In
other words, could not all models potentially be performing single-action compaction (SAC) by default? To
do so would roughly correspond to maintaining asemantic stateacross long-context workflows.
We propose the notion of a Semantic State Space Model (SSSM). A SSSM is a model post-trained to (1)
comprehend an input language description of a state of a conversation, (2) reason about the appropriate next
action or about the task at hand, (3) take an action, (4) register its outcome, and (5) update the language
description of the conversation’s state with the reasoning conclusions, action decisions, and action outcomes in
a way that allows a separate inference instance of the SSSM to continue the conversation toward completion.
The notion of a SSSM is closely related to that of a State-Space Model [19, 20, 18]. Unlike an SSM, which
maintains a black-box neural state between token generations, an SSSM maintains an explainable natural
language (hence “semantic”) state between turns of a continuing conversation.
The utility of SSSMs as opposed to existing conversational models trained for growing full-history conversations
lies in their increased token efficiency – as shown in Figure 1, there is a considerable cost benefit to maintaining
short contexts. We further surmise that it is considerably more data-efficient to train semantic state-space

models due to the lack of need to teach the model to pay attention to the suitable patches of earlier context.
Ultimately, we see no reason why SSSMs could not match the performance of full-history-accumulating models,
which begs the question: Why train full-history-accumulating models in the first place?
6. Conclusion
Our experiments provide affirmative answers to all three research questions RQ1–RQ3. In particular, we found
that on long-horizon tasks, even simple end-of-conversation compaction usually matches or slightly improves
on full-history accuracy, with only modest losses in the remaining settings. We showed that on long-input
tasks, selective input reading with compaction as a fallback matches or improves (sometimes considerably) the
full-input baselines in almost every case while keeping live context short. Finally, single-action compaction
nearly preserves or improves on the baseline accuracy while carrying only a compact semantic state between
actions.
RQ1–RQ3 were motivated by the root question RQ0: “Are long contextsnecessary?” Based on the affirmative
answers to all of the above, we conclude that long contexts are not necessary for the completion of “long-context”
tasks. This is far from surprising. After all, the very motivation behind the definition of computability rests
on the assumption that anything computable may be computed by comprehending only a bounded amount of
input at a time and maintaining only a finite state of mind [44].
Our evidence does not rule out the existence of tasks for which long context is beneficial, nor does it prove that
every possible task can be solved with short context. It does, however, show that the standard arguments in
favor of long contexts stemming from long input and long conversational horizons are insufficient: disciplined
state maintenance and selective access remove the presumed necessity in every setting we tested. We believe
that with the appropriate adjustments made to the post-training of LMs, the context window size requirements
currently imposed on these models by the standard arguments for long contexts could be removed, and model
context window sizes could shrink drastically, significantly improving the cost of token generation on the
cloud and the speed of token generation on local inference accelerators.

A. What characterizes a good compaction?
It is a common experience of human-in-the-loop agent-aided SWE workflows that after a compaction is
performed, certain crucial information disappears from the context and has to be obtained again, slowing down
the SWE process or perhaps even confusing the model and losing crucial user preferences included in previous
instructions. Note that human-in-the-loop agent-aided SWE workflows consist of two parts: autonomous SWE
work performed by the agent, and reception and comprehension of the human’s steering feedback. Because of
this, compactions produced for such workflows need to account for not only the information the agent needs
to achieve its goals, but also for all potential information that might be relevant to follow-up autonomous
work that might be triggered as a result of the human’s feedback.
In our experimentation, we initially set out to identify the cheapest, most useful method of compaction that
can preserve as much task accuracy as possible on autonomous SWE work. We discovered that treating
compaction as a mere special case of summarization is suboptimal for this purpose. LM summarizations
generally attempt to give equal weight to all facts present in the input and are prone to overemphasize repeated
segments of the agent trace regardless of their ultimate relevance to the tail of the trace being compacted. We
explored the subject along two axes: the method (e.g., summarization or message pruning) and the information
being pruned (e.g., the entire trace or only the trace segment since the last compaction plus the contents of
the last compaction). We discovered that the best compactions are not those that faithfully capture the gist
of the agentic trace, but those that best select facts relevant to the work yet to be performed – i.e., they are
not narratives of the execution history but carefully cherry-picked briefs for further execution. In particular,
we found that the most accuracy-preserving compactions, regardless of the frequency of compaction, are those
that contain (1) a verbatim or near-verbatim copy of the input task, (2) a record of agent’s current occupation,
intentions, and planned next steps, and (3) all the artifacts that are of direct relevance to future execution,
including (3a) a decomposed plan made from the input task, (3b) a list of requirements detailing when to
consider the task complete, and any pieces of information or pointers to artifacts containing information that
is of relevance to the aforementioned two. Finally, we found that the above structure of compactions readily
extends even to workflows that are not necessarily SWE-related in their nature. We used the same compaction
structure for every type of workflow considered in this work.

E. Selective reading of long inputs
Our generalized adaptation ofmini-swe-agent, mini-agent, exposes long benchmark inputs as text files
that the agent can inspect through a bash tool. LongBench v2 uses one document file, whereas LOONG
and AA-LCR expose multiple source files. The operation ofmini-agent is straightforward. The model
receives the question and file information and then chooses which text to retrieve in order to start answering
the question. A succession of Bash-invoked searches then scan entire files, but only their returned matched
excerpts enter the model’s context.
The basic process of a single search is to identify the entities, quantities, or claims needed for the answer, and
then to read a small surrounding window to interpret the candidate evidence. Further related searches might
then be used to retrieve more candidates looked up using broader sets of synonyms. Standard commands
such as grep, sed, head, and tail are the backbone of the search process. Convenience commands provide
document sizes (doc-stats), file manifests (docs-list), bounded reads (doc-read), and search-term variants
(doc-syn) allow for more surgical readouts from files and expanded search follow-ups.
E.1. Instructions supplied to the agent.
The base system prompt gives the followingman-like tool description:
doc-read [--start CHAR] [--chars N] [--lines A:B]
Read a BOUNDED window (default 6000 chars, hard-capped at 8000). Give a
character offset window, or a 1-based inclusive line range. The header
tells you the command to read the next contiguous window. This is how you
read the document sequentially without ever exceeding your budget.
grep -n -i -E ’<regex>’ "$LONGBENCH_DOC"
Find where a name / number / phrase appears (with -n for line numbers).
Then doc-read around those lines. This is usually far faster than reading

G. Agent outlines
The templates below give outlines of the structure of compaction prompts inmini-swe-agent and mini-agent
used in this work.
G.1.mini-swe-agent
We use the releasedmini-swe-agent harness [41] v2.4, with negligible changes for environment integration
and context management. The underlying task-solving loop is fully retained.
To compact its earlier work, we use the following prompt passed as a user message once the compaction
threshold is met.
Compaction prompt
Stop work. Write only a concise handoff recap; do not run commands or call tools.
The conversation will reset to the system prompt, task, and this recap.
{persistence}
Record:
1. Objective - one line describing the required result.
2. Established facts - exact paths, relevant symbols or commands, observed values,
and important errors/output. Separate observations from unverified ideas.
3. Applied changes - each changed/created file, what changed, and whether verified.
4. Verification - exact checks run, outcomes, failures, obstacles, and workarounds.
5. Dead ends - failed approaches that should not be repeated.
6. Remaining plan - outstanding subgoals, in execution order; the immediate next
command or edit; and the condition for completion.
{handoff_details}
If needed output was truncated, give a narrow command to retrieve it.
{submission_reminder}
G.2.mini-agent
As described in Section 2, we generalize the base releasedmini-swe-agent harness into amini-agent harness
by removing SWE-specific instructions and adding instructions enabling additional classes of agentic workflows.
System prompt
You solve the supplied task by interacting with a computer through bash.
Work step by step: inspect relevant evidence, act, observe the result, and verify
that it meets the task’s requirements. Keep command output focused.
{command_rules}
{context_instructions}
User prompt
<task>
{task}
</task>
{input_details}
Available tools:
{tools}

{work_instructions}

{submission_instructions}
{recap_section}

Stop work. Write only a concise handoff recap; do not call tools.

Preserve what your next stretch needs:
1. Current progress and best answer/result, separating verified facts from assumptions.
2. Relevant evidence with exact values and source locations; changes already made,
